# AGENTS.md

Operational guide for AI coding agents working on Orbithek. This file follows the [agents.md](https://agents.md) convention; [`CLAUDE.md`](CLAUDE.md) points here. It is the single source of truth for how agents work in this repository — do not duplicate its guidance elsewhere.

> **Read this whole file before writing anything.** The project is at its very beginning: the decisions recorded now shape every later line of code.

---

## What this project is

Orbithek (called wikiwikibangbang until ADR-0153) is an open-source application written in **Go** that unifies **knowledge** (wiki pages, page tree, versions, comments) and **work** (issues, fields, workflows, boards, queries) in **one data model**.

The core idea is recorded in [ADR-0001](docs/adr/0001-unified-item-data-model.md): every piece of user-generated content is a typed **item** with properties, an optional document body, an optional workflow and typed relations. Pages and issues are item *types*, not separate systems.

**Current state:** early prototype. Besides the project's self-checks (ADR consistency, DCO rule) the module holds two prototype packages: `internal/item`, the item model with lifecycle and permissions (ADR-0001, ADR-0020 to ADR-0022), and `internal/migrate`, the import engine (ADR-0023). The item store persists to an event log on disk (`internal/wal`, `internal/storage`; ADR-0008, ADR-0025): every command is fsynced before it takes effect, and startup replays the log. Item content is encrypted with a key per item; purge and redaction destroy the key (ADR-0026). Authentication exists (`internal/auth`; ADR-0013, ADR-0027): local accounts, sessions and API tokens; the first start creates an administrator; security events go to a persisted audit trail (ADR-0029), a hash chain whose newest link the log lines witness (ADR-0123); OpenID Connect single sign-on is optional (ADR-0030). The single binary `cmd/orbithek` opens the data directory and serves the web UI, a liveness probe, the authentication API and the item API (ADR-0028, described at `/api/openapi.json`); it is released for every common platform and as a container image (ADR-0024). A buildless web UI (`internal/web`, ADR-0031) runs on top of the API; bodies are edited with ProseMirror, vendored as one pre-built bundle (ADR-0032); Markdown pasted or inserted through a dialog becomes blocks of the body in the browser, never stored as Markdown (`assets/markdown.js`, proposed, ADR-0133); drawings are made with Excalidraw on a page of its own with a looser content security policy and stored as PNG attachments that carry their scene (ADR-0053). The album lists the pictures of every readable item; inserting one copies it into the edited item (ADR-0054); copies carry their source and learn of a changed original (ADR-0055). The album is also a photo library (ADR-0177): an upload records what a picture tells about itself — capture time, place, camera, exposure, read from EXIF by `internal/photo` — as `Attachment.Photo`, sealed (codec version 45); thumbnails are made on demand and kept in memory only (`ThumbnailPixels`, `ThumbnailWorkers`, `ThumbnailCacheBytes`); the album shows pictures in folders, on a timeline (`order=taken`, `/api/album/months`), as one's own favourites (`PictureFavouriteSet` in the accounts journal), as memories of the same day in earlier years and on a map drawn by the UI (`/api/album/places`) over tiles the server fetches from `OT_MAP_TILES`; pictures are chosen many at once and labelled, moved, deleted or downloaded as one ZIP archive (`/api/album/zip`); in the folders view a picture, and every chosen one with it when it is chosen, is dragged onto a folder below the open one or above it in the trail and moved there as *Move* does (`dragged` in `assets/photoparts.js`, ADR-0184); a move keeps the file's identity: every version, deleted ones included, goes to the folder with its ID, labels, notes, rule, photo data and author in one batch (`AttachmentMovedIn` sealed for the new item, `AttachmentMovedOut`, codec version 49, `POST /api/items/{ref}/attachments/{id}/move`), its content sealed again with the new item's key first (`storage.MoveAttachmentContent`), favourites kept by the file's first version and copies finding their original where it went; a file a text shows, a protected file and a drawing with comments stay where they are, and the album says why; not offered over MCP (`Session.PlanMove`, `Session.MoveFile`, ADR-0188); files and ZIP archives exported from photo apps are unpacked in the browser (`assets/zipread.js`), and with `OT_PHOTOS_GOOGLE=on` and `OT_PHOTOS_ICLOUD=on` photos come in from Google Photos through its picker, without a grant kept beyond the import, and from shared iCloud albums through Apple's undocumented interface (`internal/photosource`); an import may leave the place behind, emptied from the file's EXIF and its XMP dropped before it is stored (`photo.StripPlace`, `place=strip`), or keep it to the one who adds it, also later per picture: every other session reads the photo data without it and gets the file without it, downloads, archives, exports and copies alike (`PlacePrivate`, `AttachmentPlaceSet`, codec version 46, ADR-0178); the map draws OpenStreetMap's tiles with its credit unless `OT_MAP_TILES` names another service or `off` (ADR-0179); a photo's place is set or removed by hand by its item's editors, in the viewer, for chosen pictures or on a map, with suggestions from a Photon place search the server asks (`OT_GEOCODER`, by default photon.komoot.io, `off`; administrators turn it off under the album's settings, `site.Places`); after that everyone but the uploader gets the file without the file's own place (`PlaceName`, `PlaceManual`, codec version 48, ADR-0181); when a photo was taken is set by hand by its item's editors, in the viewer or for chosen pictures, to one time or shifted by a span (`assets/phototime.js`), or goes back to the file's own (`PUT`/`DELETE /api/items/{ref}/attachments/{id}/taken`, `TakenManual`, `AttachmentTakenSet`, codec version 54); the stored file never changes, and every picture given out through `openFor` carries that time in its EXIF, written by `photo.SetTaken` without moving what the file holds; a copy uploaded as given is accepted (`Attachment.AsGiven`), and a video keeps its own (proposed, ADR-0198); HEIC is not taken. Videos (MP4, WebM, QuickTime) are taken into the album and handled as its pictures, up to the budget `VideoBytes` with `VideoTransferSeconds` to upload or download (`video=1`): `photo.VideoType` tells them by their bytes, `photo.ReadVideo` reads time, place, duration (`Photo.Duration`, codec version 50), size and camera from the movie header by seeking, the browser takes a poster when it uploads one, sealed beside the video as `<id>.poster` (`PUT …/poster`, `storage.StorePoster`), moved, backed up and removed with it and served as its thumbnail, and a place is removed or kept private by reading its texts as zeros (`photo.VideoWithoutPlace`), streamed; videos are not exported as pictures (ADR-0189). A video is a slide that plays from the presentation's state (`playing`), with sound in the presentation window only and neither zoom nor laser; Google Photos (`=dv`, poster `=w1600-h1600`) and shared iCloud albums (largest video derivative, poster frame as poster) bring videos within `VideoBytes` (ADR-0192). A collection is deleted from the album alone, into the trash (ADR-0193). A folder is moved from the album with what it holds, into a folder or to the top of a room, by the item's move: *Move folder* offers the places (`folderTargets`), and a folder is dragged onto a folder or the trail (`folderDrop` in `assets/photoparts.js`); into another room after a warning (ADR-0200). A folder or collection keeps an order of its slides set by hand, the first versions of its stacks (`Item.PictureOrder`, `PicturesOrdered` in the field `order`, not sealed, codec version 52): whoever may edit it moves pictures before another or to the end (`PUT /api/album/order/{ref}`, cleared with `DELETE`, `Session.PlacePictures`), stacks a caller does not read keeping their places; `GET /api/album?order=slides` lists pictures in that order, the rest by name (`item.ComparePictureNames`), with `ordered` and `orderable`; the album shows it on choosing *Order of the slides* and the presentation always, and pictures are dragged into it in the album and in the presenter's strip (`orderDrop`, `moveWithin` in `assets/photoparts.js`); not offered over MCP (ADR-0195). Faces (ADR-0194) are found in the browser with the vendored face-api (`assets/faces.js`, `assets/faceparts.js`, `vendor/face-api.js`, `vendor/face-models/`); their boxes and names are `item.Face` on a picture version (`AttachmentFacesSet`, `SetPictureFaces`, `People`, the album's `person=`), and, only while administrators turn recognition on (`site.Faces`), their 128-number vectors are kept in `<id>.faces` companion files (`storage.StoreFaceVectors`), never backed up and forgotten as a whole when it is turned off; the server compares them for suggestions (`api_faces.go`). Duplicates (ADR-0196, proposed) are found by the file's SHA-256 and by how a picture looks: a 64-bit difference hash of the picture turned upright (`photo.Fingerprint`, `assets/fingerprint.js`, held together by `internal/web/jstest/fingerprint-vector.json`), made by the server when it stores a picture and kept sealed as `Attachment.Fingerprint` (codec version 53), made for older pictures as they are compared, at most `FingerprintReads` per request, and kept in memory by SHA-256; pictures look the same within `photo.SimilarBits` bits and 2 % of proportions; before files are added to a folder or a collection the browser asks `POST /api/album/duplicates` (at most `DuplicateChecks` files) and lets the person skip duplicates, ticked by default (`assets/duplicates.js`); the view deletes them all at once after a warning, one picture of every set of the same file staying (one a text shows or the reader may not delete, else the largest, else the oldest) and pictures that only look the same only when ticked (`assets/duplicateparts.js`); the view *Duplicates* shows the groups `GET /api/album/duplicates` finds among the readable stacks, a copy and its original never one group; not offered over MCP. Every picture of the album exports as PNG or JPEG — the stored file when it is in that format, else converted in the browser from the download its reader makes anyway — and a drawing also as SVG, drawn from its scene by the drawing page in a hidden frame with its fonts embedded; whoever sees a picture may export it, and nothing is added to the server (`assets/picexport.js`, ADR-0173). The pictures the album shows — a folder, narrowed by its filters — are presented as slides ordered by name: the click opens a presentation window for the projector and turns the album's window into the presenter's, with the next slide, the speaker's notes, the time and every slide; the two windows of one browser talk over a `BroadcastChannel`, step forward and back, zoom about a point of the picture and share a laser pointer and a black screen, nothing of it on the server; a picture's notes are plain text kept on its stack's first version, so every version of a drawing shows them, written by whoever may edit its item (`PUT /api/items/{ref}/attachments/{id}/notes`, `AttachmentNotesSet`, codec version 44), sealed and scanned like every text (`assets/present.js`, `assets/present-parts.js`, ADR-0176). Whoever may edit a picture renames it from its card's menu: every live version takes the name in one event (`AttachmentRenamed`, codec version 47, `PUT /api/items/{ref}/attachments/{id}/name`), the extension and a drawing's marker are kept, copies in other items keep theirs, and the drawing editor names a new version after the drawing's current name, read from the download's `Content-Disposition` (`assets/filename.js`), instead of the caption (ADR-0180). Every file of an item is renamed the same way from the item's file list, with *Rename* beside *Delete* for whoever may edit it; the album and the list share `assets/rename.js` (`Session.RenameFile`, ADR-0182). A PowerPoint presentation (`.pptx`, `.ppsx`) chosen under the album's *Upload* or dropped onto a folder becomes a folder of its own: the browser reads the slides' order, hidden slides, titles and notes from the file (`assets/pptx.js`, its own small XML reader over `assets/zipread.js`), draws each shown slide itself — `assets/pptxscene.js` resolves theme, master, layout, placeholders, text styles, shapes, pictures, tables and SmartArt into a scene, `assets/pptxdraw.js` lays out its text and draws it onto a canvas, charts and undecodable pictures as grey boxes the import counts — or, chosen together with the slides exported as pictures, pairs those with the slides by the numbers in their names; it uploads each slide named by its place and title and sets its notes as the picture's speaker's notes; the presentation file never reaches the server, and nothing on the server is new (proposed, ADR-0186). Pictures are added where one is: files chosen, dropped or pasted go into the open folder, or, in a collection or at the top, into a folder chosen each time (the folder listing says which are `editable`), each with the collection's labels; **Add from the album…** copies pictures into a folder or gives them a collection's labels; a change shows the album again as far as it was shown (`assets/album.js`, ADR-0187). Administrators set the corporate design (logo, colours, background, fonts, own stylesheet), kept in `site.wal` (`internal/site`, ADR-0052). Full-text search scans the in-memory state through the permission check (ADR-0033). Every item carries comments, held as events on the item and erased with it (ADR-0035). A board shows the items of one type in a space as columns of workflow states and moves them by transitions; it is a view, not a stored object (ADR-0036). Behind a reverse proxy, forwarded headers count only from the addresses in `OT_TRUSTED_PROXIES` (ADR-0037). The container image starts as root only to hand the data directory to `OT_RUN_AS` and gives root up before it opens anything (`internal/privdrop`, ADR-0038). Space administrators may check a space's web links on demand when `OT_LINKCHECK=on`; the checker never calls a non-public address (`internal/linkcheck`, ADR-0039). Content that brings in sensitive data (passwords, keys, account numbers) restricts its item to the person who saved it, in the same batch; a governance report per space lists sensitive, stale and implausible items (`internal/governance`, ADR-0040). Indicators of data protection regulations (DSG, GDPR templates; kept in `site.wal`) hold an item open to its space as a draft that only editors read, until a second person releases it (ADR-0058). Nine dots at the left of the top bar open the module switcher, as in the atlas console: Spaces, Tasks (open work across spaces) and Governance (every space's check). Several people edit a body at once in a live session with block locks (`internal/collab`, ADR-0010). Administrators download encrypted backups of a running server; `restore` brings one back (`internal/backup`, ADR-0034); `import -from backup` brings single spaces back into a data directory in use, skipping what it has and never bringing back what it deleted for good (`internal/restore`, ADR-0124). The server also backs up on a schedule to a destination — a directory, WebDAV, S3-compatible storage, FTPS or SFTP — a full backup every 14 days, incremental ones that hold only appended bytes and new files in between — and keeps the newest versions; the passphrase comes from the environment (`internal/autobackup`, ADR-0073). Operational metrics are at `/metrics` for administrators and metrics-scoped tokens (ADR-0016). AI agents reach the API through an MCP adapter, at `POST /mcp` or as the stdio command `mcp`, with exactly their caller's rights (`internal/mcp`, ADR-0012). Hosted assistants such as Claude connect with OAuth: the MCP endpoint is a resource server and the server its own authorization server; an administrator registers the assistant on the *AI access* page, each person approves it and may withdraw the approval, and its tokens count on `/mcp` only (ADR-0068). Administrators delete a space in two steps: into the trash, where it is out of everyone's sight and can be restored, then for good, which leaves tombstones and keeps the key taken (ADR-0069). Pages export as Word documents (`internal/export`, pure Go) and print as PDF; tables of pages and lists of items export as CSV (ADR-0071); pages also export as Markdown, with their pictures in a ZIP archive, and agents read a page as Markdown over MCP (proposed, ADR-0131). A type can carry catalog rules — url fields, unique and recommended fields, a periodic review with an owner — so a catalog kept in step with another system by agents or a synchronisation stays free of duplicates and has someone who answers for each entry; items are found by a property's value (`where`, also in MCP) (ADR-0074). A catalog space mirrors the interfaces of opendata.swiss on a schedule, with a dry run, keeping what was added here and withdrawing what the source dropped (ADR-0075); it is the first of the connectors that keep catalog spaces in step with their sources, set up under Administration, each run on its own schedule, credentials from the environment (`internal/connector`, ADR-0077). A connector reads CKAN or any JSON source by paths into its answer, writes its entries as items of a type it names and fills the type's fields from the source's values; it reaches only public addresses unless `OT_CONNECTOR_ALLOW_PRIVATE=on` (ADR-0127). The Atlassian import runs as a connector too, with the import's engine and origins, its items managed by the connector until an administrator cuts over (ADR-0128). An OpenAPI or Swagger description, in JSON or YAML, offers its lists; the one picked fills a JSON source's settings (ADR-0130). A JSON source reads a long list by the next page's address, a page number or an offset (ADR-0135), and may read only what changed since its last run, withdrawing nothing then, with a full run after a restart, a change of settings, on request and every few days (ADR-0140). A connector of the kind `git` mirrors a folder of a Git repository as a tree of pages: goldmark parses the Markdown and `internal/markdown` makes the blocks; `internal/gitrepo` reads GitHub, GitLab, Bitbucket, Gitea and Forgejo; a page is written only when its file changed, the Markdown kept in its origin; with `OT_GIT_FILES=on` an editor inserts one Markdown file into a text as a page below the item, shown whole, following its branch every hour or pinned to a commit (`internal/connector/files.go`, `Session.Mirror`; proposed, ADR-0138). Each data set with interfaces is one catalog page, written from everything the source says and replaced by every run; notes are comments (ADR-0080). Reads of the store run side by side; what they remember for later reads (the sensitive data scan per item, each person's findings for the bell) is guarded on its own and holds no content; listings copy only their page; `go test -tags scale -run TestScale ./internal/server/` measures a catalog of 10 690 entries (ADR-0081). Whoever may edit an item protects it from its page for people and groups, for reading and editing or for editing only (ADR-0078); the task list shows each task's labels, links those of kanbans, and filters by labels at the right. A kanban (ADR-0060) keeps columns of its own besides its workflow states, the fields its cards show and the order of cards per column; a move to a state column is the workflow's transition, and an administrator may add a missing one to the type (ADR-0076). Words or paragraphs of a body can be protected for people and groups: others read a placeholder that names who decides and may ask to read it; the passage's text is sealed in the log with a key of its own, and only those who read every passage of an item change its text (ADR-0088). Whole blocks — a heading with its section, a picture, a table, an embed, a diagram — are protected the same way, one protection per range (`Block.Secret`); others read one placeholder block per range, and the files such blocks show, every version included, are given to the protection's readers only, nowhere else (album, starmap, impact, exports, copies); the blocks are sealed with the protection's key, and erasing it deletes their files (codec version 38, `assets/protect.js`, ADR-0160). A click on any veiled passage or block, an embedded item's too, explains it and asks for access in a dialog (ADR-0161). The request becomes a task in the page's room, below the page, made by the server in the request's batch for one who may only read (actor `access-request:<requester>`): of a type with a workflow and a user field `assignee`, the ready-made task type defined if none can (`item.TypeTemplates`, `GET /api/types/templates`), assigned to the item's `owner` if they read it, else to the one who protected it, labelled `access-request`, restricted to those it concerns; `SecretRequested` carries the task (codec version 39). The owner answers requests too; deciding anywhere comments on the task and finishes it by its workflow, and finishing it while it waits declines; the page's card links the task, and requests without one keep Grant and Decline there; the list of ADR-0161 is gone (`assets/app.js`, `internal/item/accesstasks.go`, ADR-0162). A system that copies items follows the change feed (`GET /api/changes`): every event on what it watches, in log order from a cursor, naming only items it may read now; it checks its own grants at `GET /api/me/roles`, and a read token may watch (proposed, ADR-0121). A text shows BPMN diagrams with bpmn-js, vendored as a viewer and a modeler bundle under the UI's own policy: a `.bpmn` file of the item (block kind `bpmn`), or the newest version of a process of a process engine such as atlas (block kind `process`), which the server reads with a credential from the environment; administrators name the engines and may allow an operations view of counts per element (`internal/engine`, proposed, ADR-0129). A drawing holds such processes too, as pictures in its scene; a process of an engine is listed with its place in a text chunk of the saved PNG, and a page lays the live view over it (`assets/drawprocesses.js`, proposed, ADR-0142). Such a block shows its diagram, its diagram and the description of its tasks and decisions, or the description only (block field `View`); the description is read from the model in the browser (`assets/bpmndoc.js`, proposed, ADR-0143). A text also shows forms and decisions of such engines: a form as it is saved, drawn by form-js as a preview that sends nothing (block kind `form`), and the newest deployed version of a decision, drawn by dmn-js at its table, with its model's other decisions and requirements graph (block kind `decision`); form-js and dmn-js are vendored as bpmn-js is (`assets/engineviews.js`, proposed, ADR-0144). A text shows the architecture sketch of a release of such an engine's application (block kind `architecture`): the newest release with a sketch, followed on every read, or a fixed one, with the layers chosen; the server reads the SVG picture in the view the engine answers every caller alike and serves it as an image of its own address, refusing one that holds a script or reaches outside itself; on atlas, the token's reach decides which applications are offered (`assets/architecture.js`, proposed, ADR-0146). A form is chosen among those the steps of a process name and may show the list of its fields; a start form (block kind `startform`) shows the form of a public start link, filled in beforehand where the editor chose with the reader's username or mail address or the page's title or address, and the server sends it to the engine's public route without the credential (proposed, ADR-0148). The user tasks of an engine become linked tasks by rules an administrator sets on the engine's page under Administration and may try without changing anything (`assets/tasklinks.js`) — a filter by process, task and group, a space and a type, labels, the due date's field and the states an ended task goes to: every minute `internal/tasklink` reads the open tasks with `OT_ENGINE_<ID>_TASKLIST_TOKEN`, makes the item of a new one restricted to the synchronisation, in the same batch, and ends the item of one that is gone by its transition; an item carries `Linked` and `LinkedFields`, the engine owns its title and those fields, and people may not finish it, restrict it, move it to another space or remove it while it is open; each person connects their account to an engine by OAuth under *Account* (`internal/engineauth`), the connection and its sealed refresh token kept in `connections.wal`, which is not backed up (`internal/engineconn`); each open linked item is read and edited by the connected people whose own task list at the engine holds its task, read with their grant every two minutes; its page and the task dialog (`assets/taskdialog.js`) take it on, give it back and complete it at the engine with its form, and a card moved to a finished state opens the dialog; with `OT_ENGINE_<ID>_EVENTS_TOKEN` the rounds follow the engine's feed of task facts, so a cancelled task is told from a completed one, its cursor in `taskcursors.json`, not backed up; boards and pages say when an engine was last read; a task list in a text selects its tasks by a label or by a query (block field `Query`, codec version 37) (proposed, partial, ADR-0151). An engine that offers connected systems is connected from its page with one approval at the engine: the server names itself by its client metadata document (`GET /api/engines/client-metadata`) and an Ed25519 key kept sealed in `connections.wal`, authenticates with signed assertions, and keeps the engine's system grant there under a subject no account has; `engine.Reader` takes every credential the environment does not set from that grant, people connect through the document — silently, on the first page of a session, where the engine approved them beforehand and they have not ended a connection themselves —, a task that leaves a list read with the grant is ended only on the engine's word, and an item whose task can no longer be followed is detached: its import event recorded again without the link, its origin kept (`Store.DetachTask`, `assets/engineconn.js`, ADR-0152). A query language selects items by their fields — conditions joined with AND, OR and NOT, and ORDER BY — in the view *Query*, at `GET /api/items?query=…`, in the CSV export and with the MCP tool `query_items`; `internal/query` parses it, `Session.Select` evaluates it over the live state as the caller reads it (proposed, ADR-0136). The starmap draws one space's readable items, their pictures and the labels they share, with the tree, relations, mentions, embeds and the origins of copied pictures as edges and related items of other spaces at its edge, derived per request within the budget `StarmapNodes` and laid out in the browser by a seeded simulation; nothing on it names an item the reader may not read, not even as a count (`Session.Starmap`, `assets/starmap.js`, ADR-0157). The starmap of all rooms (`#/starmap/*`, `GET /api/starmap`, `Session.StarmapAll`) holds every readable item of every room within the same budget, pictures left out, and beyond it a bubble per room and type as big as its items with edges counting the links between them; a label (`?label=`) narrows it to the items that carry it (ADR-0191). The map moves under a live force simulation that cools to rest (Barnes–Hut above a few dozen nodes, settled at once for reduced motion); a dragged node pulls its neighbours, pointing lights a neighbourhood, captions fade with the zoom, and a double-click separates a node with its neighbourhood at a depth of one to three, with a drill path in the address that Escape steps back (`assets/starmap-sim.js`, ADR-0158). From a node's panel, an impact view shows what depends on an item or picture, or what it depends on — children on their parent, a relation's source on its target, mentions and embeds, pictures on their item, copies on their original, never shared labels — walked by the server across rooms, breadth first to a depth of one to five or all, within the budget `ImpactNodes`, never through an unreadable item; nodes are graded by distance, and the view lists them nearest first and keeps direction and depth in the address (`Session.Impact`, `GET /api/items/{ref}/impact`, MCP `get_impact`, ADR-0159). The server measures the free space of the data directory's file system, shows it to administrators and warns them (ADR-0150); from the critical level on nothing new is created — no item, space or kanban, through the UI, the API, MCP, copies, connectors or linked tasks alike, an access request with its task refused as a whole — while reading, editing, comments, the trash and purging go on: the store refuses every batch that creates (`Store.SetNothingNew`, `storage.ErrNothingNew`, HTTP 507), and every signed-in person sees a banner from `GET /api/status`, which tells the level and no sizes; at full the wiki only reads (ADR-0163). Items with date fields stand on a time axis at `#/roadmap`: as a roadmap in lanes by label, packed into rows, or as a Gantt chart with a row per item, by a start and an end field guessed from their names or chosen; computed in the browser from the item listing, its state in the address, nothing stored (`assets/timeline.js`, `assets/roadmap.js`, proposed, ADR-0164). The labels of the items one may read stand as stars on a map of their own at `#/labelmap`, beside the room's map: a star as big as the number of items carrying its label, lines between labels carried together from `GET /api/labels?pairs=on` (`Session.LabelPairs`, pairs of the listed labels only, at most `PageItems`), a canvas whose height grows with the number of stars shown; filtered by chosen labels with or without their connected labels, a word and a least count, its state in the address, nothing stored (`assets/labelmap-graph.js`, `assets/labelmap.js`, proposed, ADR-0165). A calendar at `#/calendar` shows items with date fields on the days of a month, a week or an agenda, each type by its own date fields guessed from their names or by a chosen start and end, a span across its days; it reads only the period shown with one query of the query language, its state in the address, nothing stored; what is shown is chosen in words (room, type, assigned to me or nobody, not finished or finished, words of the text, labels), a sentence says what that shows, and the query language is offered only under Advanced with the query sent; the tasks page hands its tabs to it as such choices; the week has an axis of hours; where one may edit, an entry is dragged to another day or moved with Shift and an arrow key, each move a validated change of its date fields; on the axis of hours a meeting dropped at another hour goes there, keeping its length. **The persisted event format is a contract with every existing data directory** (ADR-0025). Never change what `item.EncodeBatch` writes — a field name, a value encoding, a role name — without raising `item.CodecVersion` and teaching the decoder the old version. `TestPersistedFormatIsStable` fails on any change; regenerating its golden file is the last step of such a change, never the fix for a failing test. `apply` must produce the same state from a decoded event as from the live one: every test in `internal/item` checks that.

**Content never reaches disk in plaintext** (ADR-0026). Anything a user can type into an item is content: if you add such a field to an event, it belongs in `item.Event.erase` and in the sealed part of the codec (`wireContent`), and `internal/storage` must show it does not appear in the event file. `keys.wal` is as precious as `events.wal`: without it all content is lost.

**Every resource budget lives in `internal/budget`** (ADR-0015). A new bound on what a caller can make the server hold — a size, a count, a number of sessions — is a field of `budget.Budgets`, read with `budget.Get()`, never a constant in the package that uses it. A bound that is not a budget (a security policy, a file-format limit) is classified with its reason in `internal/budget/registry_test.go`; the test fails on any `max…` constant or reading ceiling that is neither.

**Every route is authenticated unless it says otherwise** (ADR-0011, ADR-0027). Declare `Access: Public` only for what an anonymous caller may see, and add it to `publicAPI` in the server tests, and add the route to the table in `internal/server`, never to a mux directly. Handlers reach the item store only through `storage.DB.Read`/`Write`. Never log or audit a password, session or token secret — the generated first-administrator password is the one deliberate exception. A security-relevant action records an `audit.Entry` after it succeeded.

**The MCP adapter only calls the public API** (ADR-0012). A tool is one HTTP request with the caller's credential, never an internal call; the adapter holds no credential of its own. Offering a new route as a tool is a decision: destructive, permission-changing and credential routes are deliberately not offered, and `internal/mcp/tools.go` says so.

**Every user-visible UI string comes from the catalogue** (ADR-0017). Write `t("area.key", { name })` and add the key to `internal/web/static/assets/locales/en.js`, the source; add the German text to `de.js` in the same change, in Swiss spelling (ss, never ß). Keys are literals so the tests can find them. Content (titles, type, field and state names) is not translated. A change to what people see or can do updates the user manual, `internal/web/static/assets/manual/en.md` and `de.md`, in the same change; both keep the same outline of headings (ADR-0183). Two checks hold changes to this (ADR-0185). A test fails when a manual names in bold a label its catalogue does not have: rename the label in the manual as the UI now calls it, or list bold text that is no label (a key, a symbol, a concept) in `internal/web/manual_terms.txt` with a reason. On pull requests, the job `Manual (user-visible changes)` warns when catalogue values, routes, views or UI modules are added or changed and not every manual is: update the manuals, or write a line of its own `Manual: not needed — <reason>` into the pull request description.

**UI code never turns a string into markup or code** (ADR-0014, ADR-0031). Create elements with `h()` from `internal/web/static/assets/dom.js`; `TestNoMarkupFromStrings` forbids `innerHTML` and its relatives. A UI change that adds a flow extends `e2e/smoke.cjs`.

**The product ships as one binary** (ADR-0009, ADR-0024): pure Go, no CGO, web assets embedded with `go:embed`, cross-compiled for every release platform. Never add anything that breaks this — a runtime file the binary needs next to it, a C dependency, a CDN asset, a second executable.

## Project language: English

English is the project language. This is binding for everything committed to the repository:

- code: identifiers, comments, log and error messages, test names;
- documentation: ADRs, README files, architecture docs, this file;
- commit messages, branch names, pull request titles and descriptions, issues and review comments;
- the default locale and source strings of the user interface (translations are added through i18n, never hard-coded).

**Agents write in English regardless of the language of the request.** A contributor may ask in German or any other language; the conversation with that person may follow their language, but every artifact that lands in the repository is English. If you find non-English content in the repository, translate it in a separate commit rather than mixing languages in one file.

## The invariants (do not break these)

These follow from ADR-0001, accepted on 2026-10-17, and are settled. [`docs/architecture/invariants.md`](docs/architecture/invariants.md) lists them with the checks that hold them. If a task seems to require breaking one, **stop and flag it** — it needs a new or superseding ADR, not a workaround.

1. **D1 – One model for content.** User-generated content is exclusively items. Never introduce a parallel domain object (`Page`, `Issue`, …) for a single content type. System objects (users, groups, spaces, type definitions) are exempt.
2. **D2 – Stable identity.** Internal references (relations, document references, events) always use the immutable `id`, never the human-readable `key`.
3. **D3 – Validated changes.** Properties are written only through schema-validated change commands; `state` changes only through workflow transitions. The one exception is an import (ADR-0023), which sets the source's current state directly — still validated against the type's states — because imported history is data, not a replay of transitions.
4. **D4 – No shadow data in the document.** Anything queryable is a property. Relations derived from a document body are a deterministic function of the document version.
5. **D5 – One containment parent.** Every item has at most one `parent`. Permission inheritance follows containment only; every other hierarchy is a typed relation.
6. **D6 – Type-agnostic cross-cutting capabilities.** No type-specific code in search, permissions, history, comments or notifications.
7. **D7 – Identities are permanent.** An item's ID is never reused and always resolves — to the item, to the item in the trash, or to its tombstone. Deletion removes content, never identity. ([ADR-0021](docs/adr/0021-deletion-only-when-unreferenced.md))
8. **D8 – No deletion while referenced.** An item is trashed only when no live item outside its subtree references it; deleting never leaves live content pointing at it. The one exception is redaction by the erasure role, which is logged with a reason. ([ADR-0021](docs/adr/0021-deletion-only-when-unreferenced.md), [ADR-0022](docs/adr/0022-permission-model.md))
9. **D9 – Access only narrows below the space.** An item is readable (editable) only if the space role allows it and no restriction on it or its ancestors excludes the principal; restrictions never grant. ([ADR-0022](docs/adr/0022-permission-model.md))
10. **D10 – Unreadable is non-existent, and only sessions face callers.** Nothing a caller receives — errors, embeds, relations, search results, history — reveals an item the caller may not read. API and MCP code act through `Store.As(principal)` sessions, never through the trusted `Store` commands. ([ADR-0022](docs/adr/0022-permission-model.md))

## Commands

A change is not done until the whole sequence is green. CI ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) runs the same commands on every push and pull request:

```bash
gofmt -l .                 # must print nothing
go vet ./...
go test -race ./...        # includes the ADR checks in docs/adr
go test -coverprofile=cover.out ./... && go tool cover -func=cover.out | tail -1   # floor 90% (ADR-0005)
node --test "internal/web/jstest/*.test.mjs"   # UI modules that run without a browser (Node 22, no dependencies; ADR-0133)
```

Run and package the binary:

```bash
go run ./cmd/orbithek serve -addr :8080      # http://localhost:8080, data in ./data
go run ./cmd/orbithek check -data-dir data   # verify a data directory, read-only
cd e2e && npm ci && BASE_URL=http://127.0.0.1:8080 ADMIN_PASSWORD=… node smoke.cjs   # UI in Chromium, against a fresh server
                                                     # ENGINE_TOKEN=x, with OT_ENGINE_ATLAS_TOKEN=x, OT_ENGINE_ATLAS_TASKLIST_TOKEN=x and OT_ENGINE_ALLOW_PRIVATE=on on the server, adds the process engine steps
OT_TOKEN=… go run ./cmd/orbithek mcp -url http://localhost:8080   # MCP tools on stdin/stdout for a local agent
go run ./cmd/orbithek version
GOOS=windows GOARCH=arm64 CGO_ENABLED=0 go build ./cmd/orbithek   # any release platform
docker build -t orbithek:dev .               # container image
```

CI builds every release platform on every push (`cross-build`); the list must equal the matrix in [`.github/workflows/release.yml`](.github/workflows/release.yml), which `internal/repoconfig` checks. A release is cut by a `v*` tag — pushed, or created on GitHub's release page, after which the workflow attaches the archives to that release — and that is the maintainer's decision, never an agent's. A release whose archives are missing is completed by running the `Release` workflow by hand with its tag.

On pull requests CI also runs the DCO check over the proposed commits, and the manual check over what they change (ADR-0185). Run them locally before asking for review:

```bash
go run ./cmd/dcocheck origin/main HEAD
go run ./cmd/manualcheck origin/main HEAD
```

CI also compares the numbers of the decision records a pull request adds with those on `main` and in every other open pull request, and warns on the record when one is taken, naming which pull request was opened first and the next free number. Records are numbered without gaps, so two pull requests adding one at the same time clash; the job only tells it early, is advisory and never blocks a merge. Run it locally with:

```bash
GITHUB_TOKEN=… go run ./cmd/adrnumbers -repo dbuchs7/orbithek -pr 123   # exit 1 on a clash; -advisory warns and exits 0
```

The repository settings on GitHub are compared with `.github/repository-settings.json` and `.github/rulesets/*.json` once a day by the `Settings drift` workflow ([ADR-0003](docs/adr/0003-repository-governance-settings.md)). A change to a setting goes into those files by pull request first and is applied on GitHub after the merge. Run the comparison locally with:

```bash
GITHUB_TOKEN=… go run ./cmd/settingscheck -repo dbuchs7/orbithek   # exit 1 on drift
```

The default token cannot read the merge settings or the ruleset's bypass list. The workflow therefore uses the secret `SETTINGS_READ_TOKEN` (read-only, this repository, *Administration: read*) when it exists, and then runs with `-strict`, which also fails on a value it cannot read. Creating and renewing that token is the maintainer's task, never an agent's.

The ADR tests in `docs/adr` enforce file names, headings, front matter, the status rules (`Landed` requires `Accepted`; an `Open question` needs a `Question checked` month no older than a year) and that the index in `docs/adr/README.md` matches the records. A failing ADR test is fixed in the record or the index, never by loosening the test.

When a command is added (linters, end-to-end tests, a `Makefile` target), add it here and to CI in the same pull request.

`main` is protected by the ruleset in [`.github/rulesets/protect-main.json`](.github/rulesets/protect-main.json) ([ADR-0003](docs/adr/0003-repository-governance-settings.md)): every change goes through a pull request with green required checks; direct pushes and force pushes to `main` are rejected. **Never rename a CI job without updating the ruleset in the same pull request** — required checks are matched by job name, and a renamed job blocks every merge. `internal/repoconfig` tests this.

## How to approach a task

1. **Read the relevant ADRs** in [`docs/adr/`](docs/adr/) before designing anything. They explain *why*.
2. **Check the invariants** above against your plan *before* writing code.
3. **Work test-first.** Write a failing test that states the intended behaviour, make it pass with the minimum code, then refactor. A bug fix starts with a failing regression test.
4. **Run the full check sequence** (see Commands) until green, including `-race`.
5. **Record architectural decisions.** If your change makes or alters an architectural decision, write an ADR instead of silently diverging:
   - copy [`docs/adr/template.md`](docs/adr/template.md) to `docs/adr/NNNN-<slug>.md`, using the next free number;
   - add a row to the index in [`docs/adr/README.md`](docs/adr/README.md);
   - new records are `Proposed` / `Not started`; `Implementation: Landed` requires `Status: Accepted`;
   - an accepted decision is never edited in substance — supersede it with a new ADR.
   - Present the strongest form of every rejected option before rejecting it, and list what the decision could not settle under *Open questions*.
6. **Keep changes small and focused.** One concern per pull request; no drive-by refactoring.

## Style

- Go code follows `gofmt` and the conventions of [Effective Go](https://go.dev/doc/effective_go).
- Prefer the standard library; every new dependency needs a reason in the pull request (and an ADR if it is architectural, e.g. storage, CRDT library, search engine).
- Documentation is precise and neutral: no marketing language, no unverified claims. Mark assumptions as assumptions.

### DCO sign-off: only humans sign

> **Current mode: advisory ([ADR-0019](docs/adr/0019-dco-enforcement-suspended.md)).** The DCO check reports missing sign-offs as a warning and does not fail. The rules below still apply — above all, agents never sign. Switching to enforcement is the maintainer's decision; agents do not change `DCO_MODE` on their own.

The DCO is a statement by a natural person that they have the right to submit the contribution under the project license. An AI agent cannot make that statement. Therefore:

- **Agents never write a `Signed-off-by` line anywhere** — not in commits, not in pull request descriptions, not in comments — neither with their own identity nor on behalf of a person. Do not run `git commit -s` as an agent. When an agent drafts a pull request description, it leaves the sign-off out; the human adds it.
- **Agents credit themselves only with a `Co-Authored-By` trailer** (e.g. `Co-Authored-By: Claude <noreply@anthropic.com>`).
- **The responsible human signs off** — the person who directed the agent and submits the pull request — after reviewing the diff, in one of two ways ([ADR-0018](docs/adr/0018-pull-request-level-dco-sign-off.md)):
  1. **In the pull request description (default):** edit the description and add a line of its own, outside any code block:
     `Signed-off-by: Full Name <email>`
     The DCO check re-runs on the edit and accepts every commit of the pull request that has no sign-off of its own. On squash merge, GitHub copies the description into the commit message, so the sign-off lands in the history of `main`.
  2. **On the commits:** `git rebase --signoff origin/main` on the pull request branch, then `git push --force-with-lease`.
- **By signing off, the human takes responsibility** for every commit of the pull request, including agent-written code: in particular that it does not contain code copied from sources with incompatible or unknown licenses.
- A sign-off that names an AI agent or a bot fails the check wherever it appears, and a human sign-off elsewhere does not cure it.
- Pull requests are merged by **squash** only, after the checks have finished. Once enforcement is on, a pull request without a human sign-off is not merged.
- Agents act on GitHub under the maintainer's account, so GitHub cannot tell an agent's edit from the maintainer's. The check enforces the *form* of the rule; that only a human writes the line is enforced by this guide.

Before adding a dependency, check that its license is compatible with AGPL-3.0, name the license in the pull request, and add the module with its version, license and any NOTICE to `THIRD_PARTY_NOTICES.md` (a test in `internal/repoconfig` checks the list against `go.mod`). Current dependencies: go-oidc, go-jose (Apache-2.0) and x/oauth2 (BSD-3-Clause), for OIDC only (ADR-0030); x/crypto (BSD-3-Clause), for its SSH client, used by backups to SFTP only (ADR-0073); go.yaml.in/yaml/v3 (MIT and Apache-2.0), to read API descriptions in YAML (ADR-0130). goldmark (MIT), as the Markdown parser only, never its renderer (ADR-0138). golang.org/x/net (BSD-3-Clause), for its HTML parser only, to read web pages (ADR-0208). Never copy code from sources whose license is incompatible or unknown.
